# 包管理工具

## 1、npm

### 1）初始化 package.json

```bash
npm init
# 或直接生成
npm init -y
```

### 2）切换 npm 镜像

```bash
# 切换到官方源
npm config set registry https://registry.npmjs.org

# 切换到淘宝 npm 镜像
npm config set registry https://registry.npmmirror.com

# 查看当前镜像
npm config get registry
```

## 2、package.json 属性认识

`package.json` 是一个对象，属性如下：

### 1）name

是项目的名称；

### 2）version

是当前项目的版本号（X.Y.Z），版本号要遵循 [semver 规范](https://semver.org/lang/zh-CN/)

X 主版本号（major）

Y 次版本号（minor）

Z 修订号（patch）

### 3）description

是描述信息，很多时候是作为项目的基本描述；

### 4）author

是作者相关信息（发布时用到）；

### 5）license

是开源协议（发布时用到）；

### 6）private

属性记录当前的项目是否是私有的；

当值为 true 时，npm 是不能发布它的，这是防止私有项目或模块发布出去的方式。

### 7）main

设置程序的入口，也就是导入包时，所读取的文件，导出的东西都在当前文件；

### 8）scripts

用来配置执行脚本，例：

```json
{
  "name": "",
  "version": "",
  "description": "",
  "scripts": {
    "build": "tsc",
    "start": "tsc --init"
  }
}
```

执行是：npm run build，build 是根据你 scripts 中定义的 key。

注：常用的 start、 test、stop、restart可以省略掉run直接通过 npm start等方式运行。

### 9）dependencies

指定无论开发环境还是生成环境都需要依赖的包；

```bash
npm install axios -D
# 或
npm i axios
```

注：也就说你开发依赖包的时候，如果你的依赖包，依赖了第三方包的时候，就要下载到 dependencies 中。

### 10）devDependencies

一些包在生产环境是不需要的，比如 webpack、babel 等；

```bash
npm install axios --save-dev
```

### 11）peerDependencies

依赖关系是对等依赖，也就是你依赖的一个包，它必须是以另外一个宿主包为前提的，例如 element-plus 必须依赖 vue3；

### 12）包版本

```json
{
  "dependencies": {
    "typescript": "^5.3.3"
  }
}
```

以 typescript 为例子，"^5.3.3" 和 "~5.3.3" 的区别：

① ^x.y.z：表示 x 是保持不变的，y 和 z 永远安装最新的版本；

② ~x.y.z：表示 x 和 y 保持不变的，z 永远安装最新的版本；

### 13）engines

用于指定Node和NPM的版本号

```json
{
   "engines": {
    "node": ">=16.0.0",
    "pnpm": ">8.0.0"
  }
}
```

### 14）os

指定所在的操作系统，例："os" : [ "darwin", "linux" ]

### 15）browserslist

用于配置打包后的JavaScript浏览器的兼容情况（也可以写一个 `.browserslistrc` 文件，在里面配置）

```json
{
  "browserslist": [
    "last 2 versions",
    "> 1%",
    "IE 11"
  ]
}
```

## 5、发布 npmjs.com

本仓库是 pnpm workspace 管理的多包仓库，统一使用
[Changesets](https://github.com/changesets/changesets) 管理版本号、更新日志和 npm 发布。

> 从现在开始，本仓库只按照下面的流程发布。不要逐个进入子包执行
> `npm publish`，也不要直接修改多个子包的版本号。

### 1）发布前准备

发布人需要满足以下条件：

- 拥有 npm 账号，并有权发布 `@mt-kit/*` 作用域下的包。
- 本地使用 Node.js 22 或更高版本、pnpm 10 或更高版本。
- npm registry 必须是官方源，而不是淘宝等镜像源。
- 从 `main` 分支发布，并确保本地没有未提交的修改。

首次在电脑上发布时执行：

```bash
# 确保使用 npm 官方源
npm config set registry https://registry.npmjs.org/

# 登录 npm；按照页面提示完成登录和双重验证
npm login --registry=https://registry.npmjs.org/

# 确认当前登录账号
npm whoami --registry=https://registry.npmjs.org/
```

每次发布前执行：

```bash
git switch main
git pull --ff-only
git status --short
pnpm install --frozen-lockfile
```

`git status --short` 应当没有输出。如果存在未提交文件，应先确认并处理，不能把无关修改混入发布提交。

### 2）记录需要发布的包

功能或修复开发完成后，在提交代码前执行：

```bash
pnpm exec changeset
```

根据提示完成以下选择：

1. 选择本次有改动的一个或多个包。
2. 为每个包选择版本升级类型。
3. 填写简短、清楚的更新说明。

版本类型按照 [SemVer](https://semver.org/lang/zh-CN/) 选择：

| 类型 | 什么时候使用 | 示例 |
| --- | --- | --- |
| `patch` | 修复问题，并且兼容原来的用法 | `1.2.3` → `1.2.4` |
| `minor` | 增加兼容旧版本的新功能 | `1.2.3` → `1.3.0` |
| `major` | 存在不兼容的 API 或行为变化 | `1.2.3` → `2.0.0` |

命令会在 `.changeset/` 中生成一个 Markdown 文件。该文件需要和功能代码一起提交：

```bash
git add .
git commit -m "feat: 描述本次改动"
git push
```

一个 Changeset 可以同时包含多个包，例如：

```markdown
---
"@mt-kit/utils": patch
"@mt-kit/vue-hooks": minor
---

修复工具函数问题，并增加新的 Vue Hook。
```

没有影响 npm 包的修改，例如只调整仓库内部文档，可以不创建 Changeset。

### 3）生成正式版本

准备发布时，先确保所有待发布代码和 Changeset 都已经合并到 `main`，然后执行：

```bash
# 根据 .changeset 中的记录更新版本号和 CHANGELOG
pnpm exec changeset version

# 更新 pnpm-lock.yaml 中的工作区版本
pnpm install
```

Changesets 会自动完成以下工作：

- 更新需要发布的子包版本号。
- 更新对应的 `CHANGELOG.md`。
- 必要时更新内部包之间的依赖版本。
- 删除已经使用过的 `.changeset/*.md` 文件。

执行后必须检查修改内容：

```bash
git status --short
git diff
```

重点确认：

- 只有本次计划发布的包和必要的内部依赖被升级。
- `major`、`minor`、`patch` 是否选择正确。
- CHANGELOG 内容是否清楚。
- `pnpm-lock.yaml` 是否已经同步更新。

### 4）构建并检查发布内容

先构建所有包：

```bash
pnpm run build:check
```

再检查每个待发布包：

- `package.json` 中的 `name`、`version`、`files`、`exports` 是否正确。
- `dist` 等构建产物是否存在。
- README 中的安装方式和示例是否仍然有效。
- 新增的运行时依赖是否放在 `dependencies` 或 `peerDependencies` 中。
- 不应发布的文件是否已通过 `files` 或 `.npmignore` 排除。

可以在对应子包目录中预览 npm 实际会发布的文件。例如：

```bash
cd packages-utils
npm pack --dry-run
cd ..
```

如果检查失败，修复后重新构建；不要带着已知错误继续发布。

### 5）提交版本变更

确认版本和构建结果无误后，先提交版本变更，再发布：

```bash
git add .
git commit -m "chore: release packages"
```

`changeset publish` 会根据当前提交创建 Git 标签，因此版本提交必须发生在发布之前。版本提交之后、执行发布之前，不要再插入其他提交。

### 6）一次发布多个包

执行：

```bash
pnpm exec changeset publish
```

Changesets 会遍历 workspace 中的包，查询 npm 上已有的版本，并只发布版本号尚未存在的公开包。一次命令可以发布多个包。

本仓库的 `.changeset/config.json` 已做以下配置：

- npm 包默认按照公开包发布。
- `mock` 和 `demo-vue` 被忽略。
- `private: true` 的包不会发布到 npm。
- 内部依赖发生必要变化时，关联包至少升级 patch 版本。

如果 npm 账号启用了双重验证，按照终端提示输入一次性验证码。不要把 npm 密码、验证码或访问令牌写入仓库。

### 7）发布后验证

根据发布输出逐个确认包版本，例如：

```bash
npm view @mt-kit/utils version
npm view @mt-kit/vue-hooks version
```

### 8）发布失败怎么处理

#### 部分包已经发布成功

不要撤销或覆盖已经发布的版本，也不要使用 `npm unpublish --force`。修复登录、权限或包配置问题后，重新执行：

```bash
pnpm exec changeset publish
```

Changesets 会跳过 npm 上已经存在的版本，继续发布剩余的包。

#### 提示版本已经存在

npm 不允许覆盖已经发布的同名同版本包。先检查线上版本：

```bash
npm view 包名 version
```

如果代码有新改动，应重新创建 Changeset、生成新版本，然后再发布，不能重复使用原版本号。

#### 提示 401 或 403

依次检查：

```bash
npm config get registry
npm whoami --registry=https://registry.npmjs.org/
npm access list packages
```

确认正在使用 npm 官方源、登录没有失效，并且当前账号拥有 `@mt-kit` 包的发布权限。

#### 提示构建文件不存在

检查包的 `files`、`main`、`module`、`types` 和 `exports`，然后重新执行：

```bash
pnpm run build:check
```

### 9）禁止事项

- 不要在功能分支或存在未提交修改的工作区发布。
- 不要手动逐个修改多个包的版本号。
- 不要使用 `pnpm -r publish` 绕过 Changesets。
- 不要从仓库根目录直接执行 `npm publish`。
- 不要重复发布 npm 上已经存在的版本号。
- 不要为了修复普通问题而强制撤销已经发布的版本。
- 不要提交 `.npmrc` 中的 token、npm 密码或双重验证码。
- 当前 `pnpm run publish:ci` 没有包含完整的版本生成和发布前检查流程，日常发布不要使用它。
